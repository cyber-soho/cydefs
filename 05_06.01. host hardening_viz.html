Lesson 1.1

What hardening means

10 min

A newly installed operating system is configured for compatibility, not for security. The installer enables services that most people never use, keeps well-known accounts such as Guest, and leaves settings at values that make every feature work on the first day. Hardening is the deliberate process of changing that default state: every component that the host does not need for its role is removed, disabled, or restricted, and every component that stays is configured to its safest working value.

The attack surface

The attack surface of a host is the complete set of points through which an unauthorized person or program can interact with it. For a server or a workstation, the attack surface has five measurable parts:

  • Listening services — programs that wait for network connections on a port. A port is a 16-bit number (0 to 65535) that identifies one service endpoint for TCP (Transmission Control Protocol) or UDP (User Datagram Protocol). A service that listens is code that anyone who can reach the port may execute remotely.
  • Accounts — every enabled account is a credential that can be guessed, stolen, or reused.
  • Installed software — every package carries its own defects; software that is not installed cannot be exploited.
  • Enabled features and protocols — legacy protocol versions and optional features add code paths that are often less tested.
  • Configuration values — password rules, timeouts, logging switches, and permission defaults.

Each part can be counted. A host that listens on eight ports has a larger attack surface than the same host listening on two. Hardening is therefore measurable: the count before and the count after are two numbers that belong in the Course Procedure Manual.

Least functionality and least privilege

LAB_02 applied the principle of least privilege to accounts: a user receives only the rights that the role needs. Hardening applies the parallel principle of least functionality to systems: a host runs only the functions that its role needs. The NIST (National Institute of Standards and Technology) catalogue of security controls names this principle explicitly (Special Publication 800-53, control CM-7 "Least Functionality"). The two principles reinforce each other: an accountant who cannot install software (least privilege) on a workstation that offers no network service (least functionality) is protected by two independent decisions.

The four hardening actions

Every hardening step belongs to one of four actions. Naming the action keeps the checklist precise.

ActionMeaningExample on a NorthMaple host
RemoveUninstall software that the role does not need.Purge the database engine left on the file server by the installation image.

RestrictKeep the function but limit who or what may use it.Keep SSH (Secure Shell) but allow it only from the administrator workstation.

The role decides

Hardening is never "switch everything off". A public web server must accept connections on ports 80 and 443 or it stops being a web server. A file server must offer its file-sharing port to the workstations. A workstation, in contrast, normally needs no inbound connection at all. The reference for every decision is the role of the host in the company: the zoning table of LAB_01 says where the host sits and which traffic may reach it, and the role table of LAB_02 says who uses it. Hardening translates those two tables into the configuration of the host itself.

Working safely

Two rules protect you from breaking your own laboratory. First, take a snapshot of the virtual machine before the first change; a snapshot is a saved state to which the machine can return in seconds. Second, apply one change at a time and test the role after each change — for example, open a shared folder after disabling a service on the file server. A hardening step that breaks the role is reverted and documented in the "problems met" section of the manual, not silently forgotten.

Lesson 1.2

Hardening measures for Windows and Linux hosts

12 min

This lesson turns the four actions of Lesson 1.1 into concrete settings on the two operating systems of the NorthMaple laboratory. The settings are grouped in the four areas named in the course plan for Windows — accounts, services, updates, security policies — and in the three areas named for Linux — services, SSH (Secure Shell) settings, updates. Each item below is an entry of the ten-item checklist that students apply in LAB_03.

Windows hosts

Accounts. Windows creates two well-known local accounts: Guest and the built-in Administrator. Both have predictable names, and the built-in Administrator has a predictable SID (Security Identifier) that always ends in -500. An attacker who guesses passwords starts with these two names. The hardening measures are: disable Guest, disable the built-in Administrator and use the named administrator account created in LAB_02, require a minimum password length (12 characters in this course; the CIS (Center for Internet Security) Benchmark for domain members recommends 14), and set an account lockout threshold (five failed attempts) so that password guessing stops after a few tries. The command net accounts displays the current policy; the Local Security Policy console (secpol.msc) edits it graphically.

Services. A Windows service is a program that runs in the background without a user session. The Services console (services.msc) and the PowerShell cmdlets Get-Service and Set-Service control them. Typical services to disable on NorthMaple workstations and servers: Remote Registry (allows remote edits of the registry), the Xbox services on a business workstation, and the print spooler on a server that never prints. A separate but related measure is the removal of SMB (Server Message Block) version 1, an obsolete file-sharing protocol version that worms used to spread in 2017; the cmdlet Get-SmbServerConfiguration shows whether it is enabled.

Updates. Windows Update installs the corrections that Microsoft publishes every month. The hardening measure is not one setting but a state: updates are automatic, and the newest installed update is recent. Get-HotFix lists the installed updates with their dates; a host whose newest update is older than thirty days is behind.

Security policies. Three switches matter most for a small company. UAC (User Account Control) asks for consent before an administrative action, so malware running with a user's rights cannot silently elevate; its registry value is EnableLUA = 1. Microsoft Defender Antivirus real-time protection scans files as they are opened; Get-MpComputerStatus reports it. Audit logging of logon events records who signed in and when; the events feed the detection work of LAB_04.

Linux hosts

Services. On modern distributions, systemd manages services as units. systemctl list-units --type=service --state=running lists what runs; sudo ss -tulpn lists what listens; sudo systemctl disable --now <unit> stops a unit and removes it from the boot sequence; sudo apt purge <package> removes the software completely. Units commonly disabled on a NorthMaple server: avahi-daemon (network announcements), cups (printing), rpcbind (remote procedure calls for a file protocol the company does not use).

SSH settings. SSH is the administrative door of every Linux host, so its server configuration file /etc/ssh/sshd_config receives the most attention. Four settings form the baseline of this course: PermitRootLogin no (administrators log in with their own account and use sudo, as configured in LAB_02), PasswordAuthentication no (keys instead of passwords — only after a working key has been installed for the administrator, otherwise you lock yourself out), MaxAuthTries 3 (three attempts per connection), and X11Forwarding no. Two commands protect you from mistakes: sudo sshd -t validates the file before a restart, and sudo sshd -T prints the effective configuration, including defaults that are not written in the file. Keep the current session open until a second session has confirmed that the new settings work.

Updates. sudo apt update && sudo apt upgrade installs the corrections available today; the package unattended-upgrades installs security corrections automatically every day, which is the right setting for a small company without a full-time administrator. On the Red Hat family the equivalent is dnf-automatic.

Accounts. No account may have an empty password (/etc/shadow shows an empty second field), unused accounts are locked with sudo passwd -l, and administration goes through the sudo group configured in LAB_02.

The before-and-after method

Every item is tested twice: once before the change (the BEFORE state) and once after (the AFTER state). The test is a command whose output can be captured in a screenshot, for example net accounts or sudo sshd -T | grep -i permitrootlogin. A checklist row is complete when it holds the item, the BEFORE evidence, the change applied, and the AFTER evidence. The script of this lesson produces the two states automatically for Windows; the script of Lesson 1.3 does the same for Linux.

Lesson 1.3

Monitoring, controlling, and remediating vulnerabilities through simple configuration management

10 min

A host hardened on Saturday is not necessarily hardened on Monday. New vulnerabilities are published every day, updates arrive every week, and settings change when software is installed or when someone "just tries something". This lesson introduces two connected practices that keep a host in its hardened state: vulnerability management and configuration management. Both are simple enough for a company of ten people when they are reduced to a written baseline, a repeated check, and a corrective action.

Vulnerabilities and how they are named

A vulnerability is a weakness in software, configuration, or procedure that an attacker can use to violate the confidentiality, integrity, or availability of a system. Publicly known software vulnerabilities receive a CVE (Common Vulnerabilities and Exposures) identifier, for example CVE-2024-3094, from the CVE Program, and a severity score from 0.0 to 10.0 under the CVSS (Common Vulnerability Scoring System) standard, published by FIRST. The NIST (National Institute of Standards and Technology) NVD (National Vulnerability Database) stores both, together with the list of affected product versions. A patch, or security update, is the corrected version of the software that removes the vulnerability.

The vulnerability management cycle

The cycle has five stages, repeated on a schedule (weekly is realistic for NorthMaple):

  1. Discover — know what you have: the inventory of hosts, software and versions. The service inventory of Lesson 1.1 is the first line of this inventory; LAB_05 extends it into the device registry.
  2. Assess — find which known vulnerabilities apply. On Linux, apt list --upgradable shows the packages with a newer version; on Windows, Windows Update shows the pending corrections; a free scanner such as Lynis (Linux) or the vulnerability scanners named in the links section can be used inside the laboratory only.
  3. Prioritize — decide the order. Two questions rank a vulnerability: how severe is it (CVSS), and how exposed is the host (a service reachable from the Internet is patched before one reachable only from the administrator workstation). The CISA Known Exploited Vulnerabilities catalogue lists the vulnerabilities that attackers actually use, which is the most useful priority signal for a small company.
  4. Remediate — apply the correction: install the update, change the configuration, disable the component, or add a compensating control (for example a firewall rule) when a patch is not yet available.
  5. Verify and document — re-run the check and record the result with its date. An unverified remediation is an assumption.

Patch management is the part of the cycle that handles updates. NIST Special Publication 800-40 (Guide to Enterprise Patch Management Planning) recommends treating patching as routine maintenance rather than as an emergency: a fixed weekly window, automatic installation of security updates, a test on a snapshot before a change on a server, and a planned restart.

Configuration management: baseline, drift, correction

Configuration management keeps every host in a known, documented, approved state. Three words define it:

  • The baseline is the written list of approved values — the ten-item checklist of Lesson 1.2 is the NorthMaple baseline.
  • Drift is any difference between the current state of a host and its baseline. Drift appears when an update resets a value, when a technician changes a setting to debug a problem, or when malware modifies the system.
  • Correction (remediation of drift) returns the setting to the baseline value, records the event, and — when the drift was intentional — updates the baseline with a written justification.

Large organisations use dedicated tools for this (Ansible, Puppet, Microsoft Intune, Group Policy); NorthMaple needs only a script that compares the host with the baseline, run automatically on a schedule. On Linux, cron runs a command at fixed times; on Windows, Task Scheduler does the same. The output of every run is appended to a log, so the log itself becomes the history of the host's configuration — the evidence that the manual asks for.

Monitoring in practice

Monitoring means reading the results, not only producing them. A weekly routine for the NorthMaple technician takes ten minutes: open the drift log of each host, treat every DRIFT line as a task, check the count of pending security updates, and note the date. Two numbers summarise the state of the company: the number of drifted items (target: zero) and the age of the oldest missing security update (target: under seven days).

Lesson 1.4

Validation of host security configurations using free baseline checklists (CIS Benchmarks)

10 min

The ten-item checklist of this course is deliberately short. Real hardening guides for one operating system contain hundreds of recommendations, each with a rationale, an audit procedure, and a remediation procedure. This lesson introduces the free, public sources of such guides, explains how a host is validated against one, and shows how the result is reported.

What a baseline checklist is

A security baseline is a published list of configuration settings with, for each setting, the recommended value and the reason. A benchmark is a baseline written so that it can be audited: every recommendation states how to check the current value and how to change it. The most widely used free benchmarks are the CIS (Center for Internet Security) Benchmarks, developed by consensus among volunteer professionals and available as PDF (Portable Document Format) documents for more than 100 technologies, including Windows 10 and 11, Windows Server, Ubuntu, Debian, and Red Hat Enterprise Linux. The PDF download is free for non-commercial use after registration on the CIS website.

Levels and profiles

Every CIS Benchmark recommendation belongs to a profile:

  • Level 1 — essential settings that can be applied to any system with little or no reduction of functionality. The ten NorthMaple items are Level 1 in spirit.
  • Level 2 — settings for environments that need more protection and accept some reduced functionality (for example, key-only SSH (Secure Shell) login, which needs key distribution first). Level 2 includes Level 1.

The benchmarks are linked to the CIS Controls introduced at Class 2: a benchmark recommendation is the technical setting; a control is the organisational practice it supports (Control 4 "Secure Configuration of Enterprise Assets and Software", Control 5 "Account Management", Control 7 "Continuous Vulnerability Management"). The reference workbook of this session maps each checklist item to its control.

Other free baselines

  • Microsoft Security Baselines — Microsoft's recommended settings for Windows and Microsoft Edge, distributed in the free Security Compliance Toolkit and documented on Microsoft Learn.
  • DISA (Defense Information Systems Agency) STIGs (Security Technical Implementation Guide) — the Security Technical Implementation Guides of the United States Defense Information Systems Agency, public and free; stricter than CIS Level 1.
  • Canadian Centre for Cyber Security baseline controls — the Canadian guidance for small and medium organisations; not a per-setting benchmark but the organisational list that a Quebec company of ten people is expected to follow.
  • Lynis — a free, open-source auditing tool for Linux that scans a host and prints hardening suggestions with a score; useful as a second opinion inside the laboratory.

Validation versus verification

Two words are often confused. Validation answers the question "does the configuration match the baseline?" — it compares values. Verification (used in Lessons 2.4 and in LAB_03 part 2) answers the question "does the control actually work?" — it performs a test, for example an attempted root login over SSH that must be refused. A complete host-security chapter contains both: the validation table proves that the settings are in place, and the test results prove that they produce the intended effect.

How to validate a host

  1. Choose the benchmark and the profile (Level 1 for every NorthMaple host).
  2. Audit each item: run the audit command or open the console named in the benchmark, and capture the observed value.
  3. Record PASS or FAIL per item with the evidence (command output or screenshot).
  4. Remediate the failures and audit again.
  5. Document every exception: an item that stays FAIL on purpose, with a written justification and, when possible, a compensating control. An exception without justification is a gap; an exception with justification is a decision.
  6. Compute the score: items passed divided by items scored (exceptions are excluded from the denominator, not counted as passes).

Automated assessment tools exist — CIS-CAT (CIS Configuration Assessment Tool) Lite (free, limited set of benchmarks), OpenSCAP (free, Linux) — but for ten items a script that reads an evidence file, as in the example below, is enough and teaches the method.

Lesson 2.1

Host-based firewalls: what they filter and how they differ from network firewalls

9 min

A firewall is a component that examines network traffic and allows or blocks it according to a list of rules. The word describes a function, not a place: the function can run in a dedicated appliance between networks, or inside the operating system of one host. This lesson defines both, explains what each one can see, and shows why NorthMaple needs both layers.

What a firewall looks at

Network traffic travels in packets. Each packet carries a header with the fields a firewall reads: the source address and destination address (IP (Internet Protocol) addresses), the protocol (TCP (Transmission Control Protocol), UDP (User Datagram Protocol) or ICMP (Internet Control Message Protocol)), and for TCP and UDP the source port and destination port. A rule is a condition on these fields plus an action. Two additional properties matter for host firewalls:

  • Direction — inbound traffic arrives at the host from the network; outbound traffic leaves the host. Inbound rules protect the services of the host; outbound rules limit what the host may contact.
  • State — a stateful firewall remembers the connections it has allowed. When the host opens a connection to a web server, the answer packets are automatically accepted because they belong to a known connection; no inbound rule is needed for them. Windows Defender Firewall, nftables (the framework behind UFW (Uncomplicated Firewall) and firewalld) and pfSense are all stateful.

Network firewall

The network firewall (the pfSense or OPNsense appliance of LAB_05) sits between zones. Every packet that crosses from one zone to another passes through it, so it enforces the zoning table: what the Internet may reach in the DMZ (Demilitarized Zone), what the user zone may reach in the server zone. It protects many hosts with one rule set, it is managed in one place, and it never depends on the configuration of the hosts behind it. Its limit is geometric: it sees only traffic that crosses it. Two workstations in the same user zone exchange packets through the switch without ever reaching the network firewall.

Host-based firewall

The host-based firewall (also called system firewall or personal firewall) runs inside the operating system of one host and filters the packets that enter and leave that host. On Windows it is Windows Defender Firewall; on Linux it is the netfilter framework of the kernel, configured through the nftables or iptables interfaces and, more simply, through the front ends UFW or firewalld. A host firewall has three properties that a network firewall cannot offer:

  1. It sees every packet addressed to the host, including packets from the same zone. It is the only layer that stops lateral movement — malware or an attacker moving from one compromised host to its neighbours.
  2. It knows the program behind a connection. Windows rules can allow a port only for a named application; a rule for port 445 does not help a malicious program that reuses the port.
  3. It travels with the host. A laptop on public Wi-Fi keeps its rules; the network firewall of the office is far away.

Its limits are the mirror image: it must be configured on every host, it can be switched off by anyone with administrative rights on that host (which is why LAB_02 removed those rights from users), and malware running as administrator can disable it.

Why two layers: defense-in-depth

The two firewalls fail differently. A wrong rule on the network firewall exposes a zone; a wrong rule on a host exposes one host. Malware that disables the host firewall still meets the network firewall on its way to another zone; an attacker who passes the network firewall through an allowed port still meets the host firewall of the target, which may accept that port only from one source address. The course's definition of defense-in-depth — several simple protections layered instead of one — is exactly this arrangement. In the resilience assessment of the Final Project, scenario 4 ("a worm tries to spread across the internal network") is answered by the host firewall; scenario 3 ("the public web server in the DMZ is compromised") is answered by both.

Default policy

Every firewall has a default policy that applies when no rule matches. The standard for hosts is default deny inbound, default allow outbound: nothing reaches the host unless a rule allows it, while the host can still download updates, resolve names and reach the file server. A firewall with "default allow inbound" is not a control; it is a list of exceptions to an open door.

Secure configuration of Windows Defender Firewall and a Linux firewall (UFW or firewalld)

The safe order of operations

  1. Work from the console of the virtual machine (the VirtualBox window or the cloud console), not only over SSH (Secure Shell) or Remote Desktop, and take a snapshot.

Lesson 2.3

Choosing firewall rules based on the role of the system (workstation versus server)

8 min

Which rules should a host have? The question has a mechanical answer: read the role of the host in the zoning table of LAB_01 and the role table of LAB_02, list the inbound services the role must offer, list who may use each service, and write one rule per pair. Everything not on the list stays covered by the default deny policy. This lesson gives the rule tables of the NorthMaple hosts and the reasoning behind each row.

Workstations

A workstation is a client: it opens connections to servers and receives replies through the stateful mechanism of the firewall. It offers no service to the network, so its inbound rule table is nearly empty. One optional rule exists: remote help from the administrator — Remote Desktop (TCP (Transmission Control Protocol) 3389) on Windows or SSH (Secure Shell) (TCP 22) on Linux — scoped to the administrator workstation only. Everything else is blocked by default, which includes the two ports that worms and ransomware use to move between workstations: the file-sharing port 445 and the older NetBIOS ports 137 to 139. On Windows, the workstation's network should be marked Public when it is unknown, so the strictest profile applies.

Reading the table

Four patterns appear in every row, and they are the checklist for any new host:

  1. Minimal — one row per service the role really offers. The web server has no file-sharing rule; the file server has no web rule.
  2. Scoped — the source is the smallest set that needs the service. "Any" appears only for the public website, which is the definition of a public service.
  3. Named and justified — a rule name with the company prefix and a one-sentence justification. The justification is what the Final Project grading checklist calls "it is justified" (0.5 point per chapter).
  4. Consistent with the zoning table — every allowed source is a zone or a host that the LAB_01 table already allows to reach the destination zone. The host rules refine the zoning table; they never contradict it.

Outbound rules: an awareness note

The default outbound policy stays allow in this course. A server, however, has no reason to browse the web. Companies with more time restrict outbound traffic from servers to updates, name resolution and time synchronisation, which stops malware on a compromised server from contacting its operator. This is a Level 2 measure, documented as future work in the manual, not a LAB_03 requirement.

The role decides, again

Lesson 1.1 said that the role decides what runs on a host. This lesson says that the role decides what the host accepts from the network. The two decisions must agree: a service that is disabled (Lesson 1.1) needs no rule, and a rule for a service that does not exist is a sign that the tables are out of date. Reviewing the two lists together, once per host, is the last step of LAB_03.

Lesson 2.4

Validating that the rules work as intended

7 min

A rule that exists is not a rule that works. The last step of LAB_03 is verification: a test for every rule, from an allowed source and from a denied source, with the observed result recorded next to the expected result. The tests are simple — a single connection attempt to one port of one of your own virtual machines — and they are legal only inside your isolated laboratory (Legal Notice, section 3).

The test matrix

The test matrix is a table with one row per test. Each row names the source (the vantage point, a host of the laboratory), the destination and port, the expected result (ALLOW or BLOCK), the observed result, and the verdict PASS or FAIL. Every rule produces at least two rows: a positive test from an allowed source (expected ALLOW) and a negative test from a denied source (expected BLOCK). The negative tests are the ones that catch mistakes: a rule that was scoped too widely passes every positive test and fails the negative one.

Reading the three outcomes

A connection attempt ends in one of three ways, and each one means something different:

  • Open (succeeded) — a service answered. For an expected ALLOW this is PASS; for an expected BLOCK it is FAIL.
  • Refused — the host answered immediately that nothing listens on that port (or a firewall rule uses reject). The packet reached the host; the firewall did not drop it. For a BLOCK test this is PASS only if the rule was meant to reject; for an ALLOW test it usually means the service is not started (check with ss -tulpn).
  • Timeout — no answer at all. The packet was dropped by a firewall (host or network), or the host is down. For an expected BLOCK with a deny rule this is the correct result.

Evidence from the logs

Every negative test that passes leaves a trace in the log of the target's firewall, which is the strongest evidence: it shows the packet arriving and being dropped. On Windows, %SystemRoot%\System32\LogFiles\Firewall\pfirewall.log contains one DROP line per packet when logging of blocked packets is on. On Ubuntu, sudo tail /var/log/ufw.log shows lines marked [UFW BLOCK] with the source address and destination port. On firewalld with --set-log-denied=all, the lines appear in journalctl -k. One screenshot of the log line, next to the test command, is the evidence of a BLOCK row.

Recording and repeating

The matrix is filled from three vantage points: the administrator workstation, the accountant workstation, and the DMZ (Demilitarized Zone) web server. Each row of the manual's validation section (N.4) holds the test, the expected result, the observed result, and the evidence.
