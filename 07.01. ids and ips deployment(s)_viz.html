1.1 What an intrusion is, and what "detecting" one means

slide6L1 · definitions

An intrusion is any action that violates the security policy of a system or a network: an outsider reading data they were never allowed to read, an employee using a right they should not have, malicious software contacting a server on the Internet, or an attempt at any of these. The word covers attempts as well as successes, because a defender wants to know about the attempt before it becomes a success.

Intrusion detection is the process of watching the events that happen in a computer system or on a network, and analysing those events for signs of an intrusion. The National Institute of Standards and Technology (NIST) describes this process in its Special Publication 800-94, "Guide to Intrusion Detection and Prevention Systems", which is the reference document for the vocabulary used in this lesson (the address is in the Links section).

An IDS (Intrusion Detection System) is the software or the appliance that automates that process. It observes traffic or host activity, compares what it sees with its detection logic, and when something matches it produces an alert: a record that says, in effect, "at this time, this rule matched this event, from this source to this destination". An IDS does not change the traffic. The packet that triggered the alert has already been delivered, or is being delivered, while the alert is written. For that reason an IDS is described as passive and out-of-band: it works on a copy of the traffic, outside the path the traffic takes.

1.2 What "preventing" adds

slide7L1 · IPS

An IPS (Intrusion Prevention System) contains everything an IDS contains and adds a response: when a match occurs it can stop the activity. The usual responses are to drop the packet (discard it silently), to reset the connection (send the two computers a message that ends the session), or to block the source address for a period of time. To do any of these before the packet reaches its destination, the IPS must be inline: physically or logically in the path of the traffic, so that every packet passes through it and waits for its verdict. NIST uses one general term, IDPS (Intrusion Detection and Prevention System), because almost every modern product can run in either mode. Snort and Suricata, the two free tools of LAB_04, are IDPS: tonight you install them as an IDS; in Class 8 you add rules; whether they ever become an IPS in your company is a design decision, and the rest of this lesson gives you the facts needed to take it.

1.3 The difference between detecting and blocking, stated precisely

slide8L1 · five properties

The two modes use the same detection logic. They differ in five measurable ways.

PropertyIDS — detection modeIPS — prevention mode
PositionOut-of-band: receives a copy of the traffic from a mirror port or a network tapInline: the traffic passes through the device
Action on a matchWrites an alert; the packet is delivered anywayWrites an alert and drops the packet, resets the session, or blocks the source
TimingAfter delivery — the alert can arrive seconds laterBefore delivery — every packet is delayed by the inspection time
Cost of a false positiveAn analyst wastes time on a harmless eventLegitimate business traffic is blocked (an availability incident)
Effect of a device failureLoss of visibility only; the network keeps workingDepends on the design: fail-open keeps traffic flowing uninspected; fail-closed cuts the link

Four words describe every possible outcome of an inspection, and every job interview in this profession asks for them. A true positive

slide9L1 · TP/FP/FN/TN
is an alert for a real attack. A false positive is an alert for an event that was not an attack. A false negative is an attack that produced no alert. A true negative is normal traffic that correctly produced nothing. The work of reducing false positives without creating false negatives is called tuning, and it is the reason a new sensor is almost always started in IDS mode: while it is out-of-band, a false positive costs a few minutes of an analyst's attention; once it is inline, the same false positive takes the web shop of Laurentide Outfitters offline.

1.4 The three detection methods

slide10L1 · detection methods

Signature-based detection compares the observed data with a list of known patterns called signatures or rules. A rule can be as simple as "the text ' OR 1=1 appears in a request to the web server". It is precise and produces few false positives for attacks that are already known; it cannot recognise an attack for which no rule exists. The rule sets you enable in Class 8 are signatures.

Anomaly-based detection first builds a baseline, a statistical description of normal activity (bytes per hour, number of connections per host, the protocols usually seen), and then raises an alert when the observed activity deviates strongly from that baseline. It can find attacks nobody has seen before, but it needs a learning period, and anything unusual but legitimate — the first monthly backup, a new application — produces false positives until the baseline is updated.

Stateful protocol analysis compares the observed behaviour of a protocol with the definition of how that protocol is supposed to behave: for example a web request that is 40,000 characters long, or file-transfer commands sent before the login step. The engine has to track the state of each session to do this, hence the name.

Most products combine all three. Suricata, for example, matches signatures, parses protocols so that rules can refer to fields such as the requested web address, and keeps per-session state to detect protocol misuse.

2.1 Four components, whatever the product

slide16-17L2 · components

The vocabulary of NIST (National Institute of Standards and Technology) Special Publication 800-94 separates every IDS (Intrusion Detection System) or IPS (Intrusion Prevention System) into four components. Small products fold several of them into one program; large deployments spread them over many machines. The components are the same in both cases.

The sensor is the component that observes traffic on a network. The agent is the same idea installed on one computer, observing that computer. Both produce events. The management server receives the events from every sensor and agent, stores them, correlates them (for example, it can notice that the same source address appears in events from three different sensors), and forwards alerts. The database server holds the events and alerts for later searching, and the console is the interface the analyst uses to read alerts, to tune rules and to manage sensors.

Tonight, in LAB_04, your Snort or Suricata installation is a sensor, and the text log it writes on the same machine is its console and database at once. That is enough for a company of the size of Laurentide Outfitters inc. In Lesson 4 you will see that the CIS (Center for Internet Security) Controls ask for something more: the alerts of every sensor and agent should end up in one place. The management server is that place.

2.2 The network-based sensor: what happens to a packet

slide18-19L2 · pipeline

A NIDS (Network-based Intrusion Detection System) watches the packets of a network segment. A NIPS (Network-based Intrusion Prevention System) does the same inline. In both, the packet goes through the same six stages, and knowing them explains most of the settings you will meet in the LAB_04 guide.

StageWhat it doesWhere you meet it in LAB_04
1 · CaptureThe network card is placed in promiscuous mode, so that it hands every frame on the wire to the sensor instead of only the frames addressed to its own hardware address.The interface name you give to Snort or Suricata on the command line; the VirtualBox setting "Promiscuous Mode: Allow All".
2 · DecodeThe headers are read layer by layer: Ethernet, then IP (Internet Protocol), then TCP (Transmission Control Protocol) or UDP (User Datagram Protocol), then the application protocol.The "decoder" and "app-layer" sections of the Suricata configuration file suricata.yaml.
3 · NormalisationFragments are reassembled into whole packets and TCP segments into whole streams, so that a rule can match a pattern that an attacker split across several packets on purpose.The "defrag" and "stream" settings; the reason a sensor needs memory.

5 · OutputEvery match is written as an alert: text lines in fast.log, structured JSON (JavaScript Object Notation) records in eve.json, and optionally a copy of the packet.The files you open with tail -f to prove that the sensor is running; the screenshots of your deliverable.

Two limits follow directly from the pipeline. First, the sensor can only inspect what it decodes, and it cannot decode an encrypted payload: for a connection protected by TLS (Transport Layer Security) it sees the addresses, the ports, the sizes and the timing, and the name of the server presented during the handshake, but not the content of the request. Second, the sensor only sees the traffic of the segment it is attached to; a packet between two computers on another switch never reaches it. Lesson 3 is about choosing the segment; the next section is about the other way to observe what encryption hides from the sensor.

2.3 The host-based agent: what it watches

slide20-21L2 · host agent

A HIDS (Host-based Intrusion Detection System) is an agent installed on one computer, the endpoint. It does not decode packets; it reads what the operating system already knows. A HIPS (Host-based Intrusion Prevention System) is the same agent with the right to block a process, a connection or a file operation. Four monitoring functions are common to almost every product:

File integrity monitoring (FIM) takes a baseline: a list of watched files with a cryptographic hash of each (usually SHA-256 (Secure Hash Algorithm, 256-bit digest)), then recomputes the hashes at intervals and reports every file that was modified, added or deleted. A hash changes when a single byte of the file changes, so an edited configuration file or a replaced system binary is detected even when its name and size did not change.

Log analysis reads the logs of the operating system and of applications — authentication logs, the Windows Security event log, web server logs — and applies rules to them: five failed logins from one address within a minute, a new administrator account, a service that stopped. Process and registry monitoring reports new processes, new scheduled tasks, new services and, on Windows, changes to the registry keys that start programs at boot. Rootkit detection compares what the operating system reports (the list of running processes, the list of files) with what the agent finds by other means, because a rootkit — the malware family you met in Class 4 — hides itself precisely by altering what the operating system reports.

The strength of the agent is that it works after decryption and inside the host: it sees the request the web server received, the file that was written and the user who did it. Its costs correspond point by point to that strength: it consumes memory and processor time on every host it protects, it must be installed and updated on every host, an intruder who becomes administrator of the host can stop it, and it sees nothing of the network around the host. The free products used in this course are https://wazuh.com/ (Wazuh, an agent plus a manager and a console, derived from OSSEC) and https://www.ossec.net/ (OSSEC itself); on Linux the same functions exist as separate tools, auditd for the system audit log and AIDE for file integrity.

2.4 Two more types you should be able to name

slide22L2 · WIDS/NBA + compare

NIST lists two further types. A WIDS (Wireless Intrusion Detection System) watches the radio side of a Wi-Fi network — rogue access points, clients being disconnected on purpose, unauthorised networks — which a wired sensor cannot observe; you will meet the reasons in Class 13. NBA (Network Behaviour Analysis) watches flow statistics (who talks to whom, how much, how often) rather than packet content, and is the natural place for anomaly-based detection from Lesson 1: a workstation that suddenly sends ten gigabytes to the Internet at 3 am is detected by the volume, not by a signature.

  3. sha256_of(path). Reads the file in 64 KB (kilobyte) pieces and feeds each piece to the hash object, then returns the 64-character hexadecimal digest. Reading in pieces is what lets a real agent hash a multi-gigabyte file without loading it into memory.

3.1 One rule decides everything

slide26-27L3 · one rule

A network sensor sees only the packets that cross the point where it is attached. This is not a limitation of a product; it is how a switched network works. A switch forwards a frame only to the port where the destination is, so a sensor attached to an ordinary port receives nothing but its own traffic and the broadcasts. Deployment is therefore a question of position: at which points of the network does the traffic you want to inspect pass, and how do you obtain a copy of it there.

The two families of positions in the title of this lesson follow from that rule. A network access point, in the sense used in this course, is a place where traffic between two zones must pass — the interfaces of the firewall and the uplinks between switches. Everything that moves from one zone to another is visible there. An endpoint is a computer itself — a server or a workstation — and the only way to observe what happens inside it is the host agent of Lesson 2.

In VirtualBox the setting is in the network adapter of the sensor machine, under Advanced: Promiscuous Mode: Allow All (the default, "Deny", gives the sensor nothing but its own traffic). Use an internal network or a host-only network shared with the machines you want to observe. On the CyberQuébec range, the sensor's interface must be allowed to receive the traffic of its pod segment; whether the platform grants promiscuous mode to a virtual interface by default is a platform setting — VERIFY WITH CYBERQUÉBEC before the lab, and keep the VirtualBox path as the fallback. On AWS (Amazon Web Services) or Azure a virtual interface cannot be put in promiscuous mode at all; the equivalent is the provider's traffic mirroring service, or installing the sensor on the same virtual machine as the service it protects.

3.4 Endpoints: which hosts get an agent, and in which order

slide30L3 · endpoints + HOME_NET

An agent on every computer is the goal; an agent on the right computers first is the plan. The order used in this course follows the value of what each host holds. First the servers of the server zone, because the company data is there and because they change rarely, which keeps file integrity alerts few and meaningful. Second the DMZ web server, because it is the most exposed host. Third the administrator's workstation, because its credentials give access to every system. Then the remaining workstations. Commercial products that add automatic containment and remote investigation to a host agent are sold as EDR (Endpoint Detection and Response); the functions you saw in Lesson 2 are their foundation.

3.5 The setting beginners get wrong: HOME_NET

Snort and Suricata rules are written with a direction. A typical rule header reads alert http $EXTERNAL_NET any -> $HOME_NET any: "alert when a web request goes from an outside address to one of ours". The variable HOME_NET is the list of address ranges that belong to the company, and EXTERNAL_NET is, by default, everything else. If HOME_NET is left at a value that does not match your lab — the installation default is often "any" or a private range you do not use — then a rule written for inbound attacks either never matches, or matches in the wrong direction and produces alerts about your own outbound traffic. For Laurentide Outfitters inc. the correct value lists the company ranges: the DMZ 10.10.10.0/24, the user zone 20.20.10.0/24, and the server range from your LAB_01 zoning table. Setting it is a required step of tonight's lab, and a wrong value is the first thing to check when the sensor "sees traffic but never alerts" in Class 8.

4.1 The CIS Controls in numbers

slide34-35L4 · CIS numbers

You met the CIS (Center for Internet Security) Critical Security Controls in Class 2 as a prioritised checklist of defences. The current version is 8.1, published in June 2024. It contains 18 Controls; each Control is a subject area (asset inventory, access control, malware defence, and so on) and is divided into safeguards — 153 in total — where each safeguard is one concrete action, written so that a technician can answer "done" or "not done". Every safeguard is assigned to one of three Implementation Groups: IG1 (Implementation Group 1, 56 safeguards, called essential cyber hygiene, the minimum for every enterprise), IG2 (Implementation Group 2, IG1 plus the safeguards for an enterprise with staff dedicated to IT and sensitive data), and IG3 (Implementation Group 3, all 153). Each safeguard also carries one security function from the NIST (National Institute of Standards and Technology) Cybersecurity Framework 2.0: Govern, Identify, Protect, Detect, Respond or Recover. The official pages are https://www.cisecurity.org/controls and https://www.cisecurity.org/controls/v8-1; the document itself is a free download after registration.

4.2 What "active defense" means in this course

slide36L4 · active defense

The measures of Classes 1 to 6 — zoning, least privilege, hardening, host firewalls — are configured once and then remain in place. They belong to the Protect function: they reduce what an attacker can do, but they do not tell anyone that an attack is happening. Active defense, as the term is used in this course, is the set of measures that operate during an attack: they observe, they alert, and where permitted they react. They belong to the Detect and Respond functions. An IDS (Intrusion Detection System) is a Detect measure. An IPS (Intrusion Prevention System) is classified by CIS as Protect, because dropping a packet is a protective action, even though the decision to drop is a detection. The alert review a technician performs is a Respond activity, and it is a person, not a product.

One clarification is necessary because the same words are used with another meaning elsewhere. In some publications "active defense" means deceiving attackers with decoy systems, or even attacking them back. Decoys are a legitimate advanced topic; attacking back is a criminal offence under section 342.1 of the Criminal Code of Canada, whatever the provocation, and it is not part of any lesson of this course.

4.4 The neighbouring controls a sensor depends on

A sensor does not stand alone in the CIS Controls. Control 8, Audit Log Management, asks that logs be collected (safeguard 8.2), centralised (8.9) and reviewed (8.11): the fast.log and eve.json files of your sensor and the authentication log of RLE 07-2 are audit logs in this sense, and an alert nobody reads satisfies nothing. Control 12, Network Infrastructure Management, asks for a secure network architecture (12.2): your zoning table is that architecture, and Lesson 3 showed that the sensor's value depends on it. Control 1, Inventory and Control of Enterprise Assets, is the reason the HOME_NET variable can be written at all: you can only list your address ranges if you know your assets. Control 10, Malware Defenses, and Control 17, Incident Response Management, are the two sides of what happens after an alert: the malware the sensor detected must be handled, and someone must have been designated in advance to handle it.

4.5 Implementation Groups: why detection comes after hygiene

slide39L4 · IGs

Control 13 contains no IG1 safeguard. The first network detection safeguard, 13.3, and the host detection safeguard, 13.2, are assigned to IG2; the prevention safeguards 13.7 and 13.8 are IG3. CIS is saying something precise with this assignment: before a company deploys sensors, it should have its IG1 hygiene in place — the asset inventory, the account management, the patching, the audit logs of 8.2, the hardening you did in LAB_03 — because a sensor watching an unpatched, uninventoried network produces alerts that nobody can act on. Laurentide Outfitters inc. is a small company, and by size it is an IG1 enterprise; it holds customer and payment data for its web shop, which is the usual reason a small enterprise adopts the IG2 detection safeguards. That is the argument you will write in the resilience assessment of the Final Project (Class 19), and the coverage report of the example below is its evidence.

  1. Snapshot the Linux machine before you install anything, so that a mistake costs one click.
  2. Install the sensor from the package source named in the guide (Suricata 8.x from the distribution's packages or the OISF (Open Information Security Foundation) repository; Snort 3 from its packages). Package names and repository addresses change — the guide is the reference, this page is not.
  3. Set HOME_NET in the configuration file (/etc/suricata/suricata.yaml for Suricata; snort.lua for Snort 3) to the company ranges: 10.10.10.0/24, 20.20.10.0/24 and the server range of your LAB_01 zoning table. Lesson 3, section 3.5, explains why this line matters more than any other.
  4. Give the sensor the traffic: attach its interface to the virtual network your company machines use, enable promiscuous mode (VirtualBox: adapter → Advanced → Promiscuous Mode: Allow All), and write down the interface name (ip -br link).
  5. Fetch a rule set (suricata-update for Suricata, which installs the free Emerging Threats Open rules; the community rules for Snort). You will not use the rules tonight; fetching them tonight saves the download during Class 8.
  6. Start the sensor on the interface with the command given in the guide, and read the start-up log until you see the engine started message and the number of rules loaded.
  7. Prove it sees traffic: from another lab machine, browse the DMZ (Demilitarized Zone) web server or ping across zones; on the sensor, watch the statistics log (/var/log/suricata/stats.log) or the packet counter of the console and confirm the numbers increase.
  8. Record the evidence: three screenshots (the engine started without errors; the HOME_NET line; the counters increasing while traffic is generated) plus an environment page for the Course Procedure Manual: machine name, interface name, HOME_NET value, sensor and rule-set versions, date.
Common pitfalls (say them before anyone meets them).
  • The sensor runs on the wrong interface (the management one) and sees nothing but its own traffic.
  • Promiscuous mode left at "Deny": counters stay at zero.
  • HOME_NET left at the installation default.
  • The sensor started twice — once as a service by the package, once by hand — and both try to open the same interface.
  • No Internet access from the machine: the rule download fails silently; the sensor still runs, which is fine for tonight.
  • Not enough memory: Suricata needs the amount stated in the guide (VERIFY BEFORE CLASS against the guide of record) — a machine with too little memory stops with an allocation error.
  • No snapshot taken before installation.
