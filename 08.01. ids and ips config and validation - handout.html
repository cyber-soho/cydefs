1.1 What a rule is Slide 8

  • Rule (also called a signature) — one line of text that gives the detection engine two instructions: which packets to examine (the header) and what to look for inside them (the options). When both are true for the same packet, the engine performs the action written first.

Specimen: rule 4 of the LAB_04 set.

alert http any any -> 10.10.10.20 80 ( msg:"LAB rule 4 - SQL tautology OR 1=1 in a request to the web shop"; flow:to_server,established; http.uri; content:"or 1=1"; nocase; classtype:web-application-attack; sid:1000004; rev:2; )

1.2 The rule header — seven fields, always in this order Slide 9 Slide 10

  • Action — what the engine does when the whole rule is true: alert (log the event — tonight, always), drop (discard; inline IPS (Intrusion Prevention System) only), pass (stop inspecting), reject (drop and send a refusal).
  • Protocol — tcp (Transmission Control Protocol), udp (User Datagram Protocol), icmp (Internet Control Message Protocol, the protocol of ping), ip; Suricata also accepts application protocols such as http, dns, tls, ssh.
  • Source address / destination address — a single IP (Internet Protocol) address, a network in CIDR (Classless Inter-Domain Routing) notation (20.20.20.0/24), a variable ($HOME_NET, $EXTERNAL_NET), a list [a,b], a negation !20.20.10.10 (every address except this one), or any.
  • Source port / destination port — a number, any, a range 1024:65535, a negation, or a variable such as $HTTP_PORTS. Port 80 = HTTP (Hypertext Transfer Protocol); 22 = SSH (Secure Shell).
  • Direction operator — -> one direction only; <> both directions; there is no <-.
  • Header first — addresses, ports and protocol are cheap comparisons, done before any content is read; a header mistake removes the rule before the content is even examined.

1.3 The rule options — what to look for, and how the alert is named Slide 11 Slide 12 Slide 13

  • Option — one item inside the round brackets, written keyword:value; or keyword;. Every option ends with a semicolon — the missing semicolon is the most frequent syntax error.
  • msg — the human-readable text printed in the alert line.
  • sid (SID, Signature Identifier) — a number unique in the whole rule set; below 1,000,000 is reserved for distributed rule sets (ET (Emerging Threats) Open); your own rules start at 1,000,000.
  • rev — the revision counter of the rule text; printed in the alert, so evidence names the exact version.
  • classtype — the category of the alert, which also assigns its priority (1 = highest) through classification.config.
  • content — the byte string that must appear; case-sensitive unless nocase follows it.
  • http.uri — a sticky buffer: the following content options search only the request URI (Uniform Resource Identifier), normalized (%20 decoded to a space).
  • flow:to_server,established — the packet goes from client to server inside a connection whose TCP handshake is complete.
  • itype:8 — the ICMP message is an echo request (type 0 = echo reply).
  • flags:S — the SYN (synchronize) flag alone: the first packet of a new connection, one alert per attempt.
  • Order — options are evaluated in the order written: http.uri must come before the content it applies to.

Suricata versus Snort 3. Suricata: http.uri; content:"UNION SELECT"; nocase;. Snort 3: http_uri; content:"UNION SELECT",nocase; (buffer with an underscore, modifier inside the content option). Everything else in the four LAB_04 rules is identical. Syntax test: suricata -T -c /etc/suricata/suricata.yaml or snort -T -c snort.lua -R local.rules (-T = test the configuration and stop).

1.4 How the engine reads a rule — and the four mistakes that make it silent Slide 14 Slide 15

  • Evaluation order — header first, options second, in the order written; alert only if every condition is true; otherwise the packet passes silently and nothing is logged.
  • Mistake 1 — wrong HOME_NET — a rule with -> $HOME_NET cannot match if the variable does not contain the destination of your test; compare it with your LAB_01 zoning table first.
  • Mistake 2 — wrong direction or port — a test going the other way does not match ->; an HTTPS (Hypertext Transfer Protocol Secure) request on 443 can never match a content rule (encrypted bytes).
  • Mistake 3 — rule not loaded — local.rules must be listed under rule-files: (or passed with -R), the engine restarted or reloaded after every edit, identifiers unique; read the "rules loaded" line.
  • Mistake 4 — case and encoding — without nocase, union select ≠ UNION SELECT; without http.uri, the engine may search raw bytes containing UNION%20SELECT.

1.5 Reading an alert line Slide 16

09/16/2026-19:20:42.990001  [**] [1:1000004:2] LAB rule 4 - SQL tautology OR 1=1 in a request to the web shop [**] [Classification: Web Application Attack] [Priority: 1] {TCP} 20.20.10.77:44121 -> 10.10.10.20:80
  • fast.log — one plain-text line per alert (/var/log/suricata/fast.log); eve.json — one JSON (JavaScript Object Notation) object per event with more fields (the EVE (Extensible Event Format) log). Snort 3: -A alert_fast.
  • Timestamp — local time of the sensor with microseconds; your evidence must show it.
  • [gid:sid:rev] — GID (Generator Identifier) 1 is the rule engine; then the signature identifier and its revision: [1:1000004:2] = rule 1000004, revision 2.
  • Message, classification, priority — from msg and classtype.
  • {PROTO} source -> destination — the packet that matched; read it against your diagram.
  • Watch alerts live — sudo tail -f /var/log/suricata/fast.log; count by rule — grep -c 1000004 /var/log/suricata/fast.log.

1.6 Your first local rule — six steps Slide 17

  1. Name the event in one plain sentence.
  2. Narrowest header that still catches it (protocol, addresses, port, direction).
  3. One or two detection options that remove noise (for example flags:S;).
  4. Bookkeeping: clear msg, classtype, sid ≥ 1,000,000, rev:1.
  5. Save in local.rules, test the syntax with -T, restart, read the "rules loaded" line.
  6. Validate with safe traffic (Lesson 3) and keep the alert screenshot for Chapter 4.

Lesson 2 — Web application security basics: injection attacks, their countermeasures, and why an IDS can help detect them

      
Slides 23–35 17 minutes · how a request becomes a database command, what goes wrong, the developer's fix, and what the sensor sees

    

    
  

  



  
2.1 How a request becomes a database command Slide 23

  
    
    
  • Web application — a program that answers HTTP (Hypertext Transfer Protocol) requests, for example the web shop of Laurentide Outfitters inc. on web-01.
    • 
    
  • Request URI (Uniform Resource Identifier) — the part of the address after the host name, e.g. /shop/search?q=tent; it carries the user's data.
    • 
    
  • SQL (Structured Query Language) — the language of relational databases; the application builds an SQL command from fixed text written by the developer plus data supplied by the user.
    • 
    
  • The question of web application security — what stops the user's data from being read as part of the command?
    • 
  


  
2.2 Injection, defined Slide 24

  
    
    
  • Injection attack — user-supplied data is placed into a command in such a way that the interpreter (database engine, shell, directory server) reads part of the data as instructions. Root cause: data and code mixed in one string.
    • 
    
  • SQL injection — the input becomes part of a database query (CWE (Common Weakness Enumeration) entry 89).
    • 
    
  • Operating-system command injection — the input becomes part of a shell command.
    • 
    
  • XSS (Cross-Site Scripting) — the input becomes part of the HTML (Hypertext Markup Language) page shown to other users; their browsers run the attacker's script.
    • 
    
  • References — OWASP (Open Worldwide Application Security Project) Top Ten category A03:2021 "Injection"; MITRE ATT&CK technique T1190 "Exploit Public-Facing Application".
    • 
  


  
2.3 Worked example — the login form Slide 25 Slide 26

  
SELECT id, username, email FROM accounts WHERE username = '' OR 1=1 --'

  
    
    
  • Concatenation — the vulnerable code glues the user name between two quotation marks: "... WHERE username = '" + username + "'".
    • 
    
  • Tautology — OR 1=1 is always true, so the WHERE filter accepts every row; the attacker's first ' closes the string early and -- comments out the developer's closing quote. Result: every account is returned.
    • 
    
  • UNION — appends the result of a second query, chosen by the attacker, to the legitimate one: ' UNION SELECT id, username, email FROM accounts -- reads other tables through a search box.
    • 
    
  • Signature fragments — or 1=1 and UNION SELECT: what rules 1000004 and 1000003 look for in the request URI.
    • 
  


  
2.4 Countermeasures — the developer's layer Slide 27 Slide 28

  
    
    
  • Parameterized query (prepared statement) — the command is written with a placeholder (WHERE username = ?) and compiled first; the user's input is bound afterwards as a value only, so it can never be parsed as SQL. The primary countermeasure.
    • 
    
  • Allow-list input validation — accept only the expected shape (letters and digits, maximum length, an integer in a range); a complement, never a replacement.
    • 
    
  • Least privilege for the database account — the application's account reaches only the tables it needs (the LAB_02 principle applied to a service account).
    • 
    
  • Error handling that does not leak — never show a database error to the user; log it, show a generic message.
    • 
    
  • WAF (Web Application Firewall) and patching — extra layers where the code cannot be changed; they reduce exposure, they do not repair the vulnerability.
    • 
    
  • Reference — OWASP SQL Injection Prevention Cheat Sheet: https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html
    • 
  


  
2.5 Why a network sensor helps — the detection layer Slide 29 Slide 30

  
    
    
  • Detection layer — the IDS (Intrusion Detection System) sees the request in transit; it cannot fix the code, but it reports the attempt (timestamp, source, request), covers what is not fixed yet, shows a campaign early (many alerts from one source), and proves that a fix works.
    • 
    
  • Limit 1 — encryption — on HTTPS the sensor sees only encrypted bytes; content rules work after TLS (Transport Layer Security) termination or on internal plain-HTTP links.
    • 
    
  • Limit 2 — evasion — letter case (answered by nocase), 2=2 instead of 1=1, comments inside keywords, encoded characters; distributed rule sets contain many rules per attack family.
    • 
    
  • Limit 3 — false positive — legitimate text that matches a rule (a forum post about SQL); every alert still needs a human.
    • 
    
  • Defense-in-depth — prevention in the code and detection on the wire are two layers of one defense, not alternatives (Final Project Chapter 7, row 3).
    •

Three rows returned by the unsafe query for an injection means the whole table leaked; zero rows from the safe query means the input was treated as a value. The sensor column is identical in both cases.

Lesson 3 — Validating that a detection system actually detects: safe, contained test traffic

      
Slides 36–47 18 minutes · running is not detecting; the validation loop; the LAB_04 test kit; negative tests; what counts as evidence

    

    
  

  



  
3.1 Running is not detecting Slide 36

  
    
    
  • Running — the process is up, the interface is open, the packet counters increase. It proves nothing about detection.
    • 
    
  • Validation — a known, harmless event generated on purpose, and the expected alert looked for in the log. Seven things can be wrong without any error message: HOME_NET, the interface, the inclusion of local.rules, one rule's syntax, the direction operator, encryption, a missing restart.
    • 
    
  • Grading rule (Final Project Chapter 4) — "at least one captured alert corresponding to your own safe, contained test traffic".
    • 
  


  
3.2 Safe and contained — a test is not an attack Slide 37

  
    
    
  • Safe — harmless to the target and to everyone else: a ping, one connection attempt, one HTTP (Hypertext Transfer Protocol) request with a text fragment; changes no data, exploits nothing, leaves nothing behind.
    • 
    
  • Contained — generated inside your isolated laboratory, from one of your virtual machines to another, on the isolated virtual network of LAB_01; never on the network of your home, employer or college.
    • 
    
  • Test versus attack — ' OR 1=1 -- sent to your own web-01 is a test; sent to any website you do not own it is an attempt at unauthorized access (Criminal Code of Canada s. 342.1). If in doubt, stop and ask the instructor.
    • 
  


  
3.3 The validation loop Slide 38

  
    
    
  • Predict — write the expected SID (Signature Identifier), or "no alert", before the test.
    • 
    
  • Generate — one action from a named machine.
    • 
    
  • Observe — sudo tail -f /var/log/suricata/fast.log, or eve.json filtered with jq (JSON (JavaScript Object Notation) events); Snort 3: -A alert_fast.
    • 
    
  • Compare — expected = observed → PASS (screenshot); anything else → FAIL (troubleshoot, rerun). Right sid but wrong addresses = FAIL (wrong machine).
    •
