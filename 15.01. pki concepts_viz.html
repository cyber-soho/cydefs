Recall — Class 14 in five points

Slide 4Recall: Class 14 in five points
  1. Symmetric encryption uses one shared key to encrypt and decrypt, for example with AES (Advanced Encryption Standard). It is fast; its problem is distributing the key safely.
  2. Asymmetric encryption uses a key pair: what the public key encrypts, only the private key decrypts; what the private key signs, anyone can verify with the public key (RSA (Rivest-Shamir-Adleman), ECC (Elliptic Curve Cryptography)).
  3. A hash function turns any input into a fixed-length digest, for example with SHA-256 (Secure Hash Algorithm, 256-bit output); changing one bit of the input changes the digest completely.
  4. Passwords are stored as salted hashes, never in clear text.
  5. Cryptography protects data in transit (on the network) and at rest (on a disk).

The question that opens today: when a server sends me its public key, how do I know it is really the key of that server? The PKI (Public Key Infrastructure) answers it.

1.1 The problem a PKI (Public Key Infrastructure) solves

Slide 7The problem a PKI (Public Key Infrastructure) solves
Key pair
Two related keys: what the private key signs, the public key verifies; what the public key encrypts, only the private key decrypts.
MITM (Man-in-the-Middle) attack
An attacker on the network path replaces the server's public key with his own, reads or changes the traffic, and forwards it. Neither side notices.
Identity–key binding
Proof that a public key really belongs to a given name. A stronger algorithm does not provide it — this is the missing piece.
PKI (Public Key Infrastructure)
The roles, policies, procedures, software and hardware that create, distribute, store, validate and revoke digital certificates, so that a computer checks the binding automatically, in milliseconds.
Slide 8Five key terms of a PKI (Public Key Infrastructure)
Digital certificate
A signed statement that binds a public key to an identity (a name) for a defined period and for defined uses.
Certificate Authority
The entity that verifies an identity, then signs the certificate that binds it to a public key.
Trust store
The list of root certificates that an operating system or a browser accepts without further proof.
Revocation
Declaring a certificate invalid before the end of its validity period.

1.2 The digital certificate (X.509 version 3)

Slide 9The X.509 v3 certificate (1/2)

X.509 version 3 — the certificate format of the Internet, defined by the ITU-T (International Telecommunication Union, Telecommunication Standardization Sector) https://www.itu.int/en/ITU-T/Pages/default.aspx and profiled by the IETF (Internet Engineering Task Force) https://www.ietf.org/ in RFC (Request for Comments) 5280 https://www.rfc-editor.org/rfc/rfc5280.

Slide 10The X.509 v3 certificate (2/2)
Signature value
The issuer hashes all the other fields and signs the hash with its private key; changing one bit makes the verification fail.
A certificate is public
Holding a copy proves nothing. Identity is proven by signing fresh data with the matching private key (Lesson 2).
PEM (Privacy-Enhanced Mail)
Base64 text between -----BEGIN CERTIFICATE----- lines; .pem, .crt or .cer.
DER (Distinguished Encoding Rules)
The same certificate in binary form; .der or .cer.
PKCS (Public-Key Cryptography Standards) #12
Certificate and private key in one password-protected file; .pfx or .p12.
CSR (Certificate Signing Request)
The request sent to a CA (Certificate Authority): public key and names, signed with the requester's private key; .csr.

1.3 Certificate Authorities and the hierarchy of trust

Slide 11The hierarchy of Certificate Authorities
Root CA (Certificate Authority)
The top of the hierarchy. Self-signed (Issuer = Subject); trusted only because it is pre-installed in trust stores; its key is kept offline in an HSM (Hardware Security Module).
Intermediate (issuing) CA (Certificate Authority)
Signed by the root; signs end-entity certificates every day; if its key is compromised, only it is revoked.
End-entity (leaf) certificate
Issued to a server, a user or a device; Basic Constraints CA:FALSE.
RA (Registration Authority)
An optional role that checks identities before the CA (Certificate Authority) signs.
Slide 12Public CA (Certificate Authority), private CA (Certificate Authority) and validation levels
Validation levels
DV (Domain Validation): control of the domain name; OV (Organization Validation): plus the legal identity of the organization; EV (Extended Validation): a stricter check of the legal entity. Browsers show the same padlock for all three.
Public CA (Certificate Authority)
Trusted by browsers worldwide, for example Let's Encrypt https://letsencrypt.org/, run by the non-profit ISRG (Internet Security Research Group) https://www.abetterinternet.org/; it certifies only names it can validate on the public Internet.
Private CA (Certificate Authority)
Run by an organization for its own names; trusted only where its root is installed — the NorthMaple lab CA (Certificate Authority) of Example 1, the pfSense Certificate Manager https://docs.netgate.com/pfsense/en/latest/certificates/index.html.
.internal
A top-level domain reserved by ICANN (Internet Corporation for Assigned Names and Numbers) on July 29, 2024 for private networks https://www.icann.org/en/board-activities-and-meetings/materials/approved-resolutions-special-meeting-of-the-icann-board-29-07-2024-en.

1.4 Trust stores and root programs

Slide 13Trust stores and root programs
Trust anchor
A root certificate in a trust store (Windows, macOS, Linux, Firefox, Chrome Root Store).
Root program
The audits and rules a CA (Certificate Authority) must satisfy to enter a trust store — for example the Mozilla CA (Certificate Authority) Certificate Program https://wiki.mozilla.org/CA or the Microsoft Trusted Root Program https://learn.microsoft.com/en-us/security/trusted-root/program-requirements.
Baseline Requirements
The rules of the CA/Browser Forum (Certification Authority/Browser Forum) https://cabforum.org/ that every public CA (Certificate Authority) must follow; audit records are shared through the CCADB (Common Certificate Authority Database) https://www.ccadb.org/.
DigiNotar (2011)
A compromised CA (Certificate Authority) whose roots were removed from every trust store: all its certificates stopped being trusted at once https://blog.mozilla.org/security/2011/08/29/fraudulent-google-com-certificate/. The trust store is the final authority.

1.5 How a browser decides to trust a website

Slide 14How a browser trusts a website (1/2)
Certificate path validation
The checks of RFC (Request for Comments) 5280, section 6, run from the leaf up to a root that is already in the trust store. One failure = a full-page warning and no request sent.
Slide 15How a browser trusts a website (2/2)
  1. Build the chain to a trusted root — else NET::ERR_CERT_AUTHORITY_INVALID.
  2. Verify every signature with the public key of the certificate above.
  3. Check the validity period — else NET::ERR_CERT_DATE_INVALID.
  4. Check the name in the SAN (Subject Alternative Name) — else NET::ERR_CERT_COMMON_NAME_INVALID.
  5. Check constraints and usage — issuers CA:TRUE, leaf allowed for server authentication.
  6. Check revocation (Lesson 3).
  7. Apply browser policy — Certificate Transparency logs https://certificate.transparency.dev/, maximum validity.
  8. Verify proof of possession — the server signs the handshake (Lesson 2).

1.6 Self-signed certificates in the NorthMaple laboratory

Slide 16Self-signed certificates in the NorthMaple lab
Self-signed certificate
Signed with its own key (Issuer = Subject). It encrypts, but nobody confirms the identity, so browsers warn — as on the pfSense page of LAB_05.
Fingerprint
The SHA-256 (Secure Hash Algorithm, 256-bit output) hash of the whole certificate, compared with the value shown on the server console before you accept it.
Acceptable in a lab only if
the fingerprint is checked, or the certificate — better, a lab root CA (Certificate Authority) — is imported into the trust store of the lab machines. Never click through certificate warnings.

    Step-by-step explanation
    1. Steps 1-3 - safety and folder. set -euo pipefail makes the script stop at the first error, so a failed command never leaves you with half a PKI (Public Key Infrastructure). The folder ~/nm-pki keeps all files together.
    2. Step 4 - the Root CA (Certificate Authority) key. openssl genpkey creates an ECC (Elliptic Curve Cryptography) private key on curve P-256 (128-bit strength). Nothing is printed: the key goes straight into nm-rootca.key.
    3. Step 5 - protect the key. chmod 600 leaves read and write rights to the owner only. In production, this key would live in an HSM (Hardware Security Module) or on an offline machine.
    4. Step 6 - the root certificate. openssl req -x509 creates a certificate instead of a request. -subj writes the DN (Distinguished Name); basicConstraints=critical,CA:TRUE allows the root to sign certificates; keyUsage=keyCertSign,cRLSign limits it to signing certificates and CRLs (Certificate Revocation Lists); -days 3650 gives ten years.
    5. Step 7 - self-signed proof. The output shows identical subject= and issuer= lines: this is what "self-signed" means.
    6. Steps 8-10 - the server request. A separate key is generated for the server. The CSR (Certificate Signing Request) carries the public key, the DN (Distinguished Name) and the SAN (Subject Alternative Name) DNS:intranet.northmaple.internal, and is signed with the server key.
    7. Step 11 - the CA (Certificate Authority) reviews the request. -verify checks the signature of the CSR (Certificate Signing Request) (self-signature verify OK): the requester really holds the matching private key.
    8. Steps 12-13 - issuance. The extension file says what the CA (Certificate Authority) allows: CA:FALSE, digitalSignature, serverAuth and the SAN (Subject Alternative Name). openssl x509 -req signs the CSR (Certificate Signing Request) with -CAkey nm-rootca.key; -CAcreateserial creates the serial-number file; -days 200 follows the maximum for public certificates since March 15, 2026.
    9. Step 14 - read the certificate. The output gives the issuer (the NorthMaple root), a random 20-byte serial number, Not Before and Not After (200 days later), and the SAN (Subject Alternative Name).
    10. Steps 15-18 - four browser decisions. With the root as trust anchor: OK. With the system trust store only: error 20 ... unable to get local issuer certificate - the chain cannot reach a trusted root. With the right host name: OK. With files.northmaple.internal: error 62 ... hostname mismatch.
    11. Step 19 - fingerprint. The SHA-256 (Secure Hash Algorithm, 256-bit output) fingerprint of the root is the value two administrators compare by phone before the root is installed anywhere.
    12. Steps 20-21 - the one-command self-signed certificate. openssl req -x509 -newkey ... -noenc creates key and certificate together; the output shows Issuer = Subject, so a browser can only trust it after it is imported or its fingerprint is verified.

    2.1 SSL (Secure Sockets Layer) and TLS (Transport Layer Security): one protocol family, several versions
    Slide 20SSL (Secure Sockets Layer) and TLS (Transport Layer Security): one family, several versions
    

    

    SSL (Secure Sockets Layer)
    The first web-security protocol (Netscape, mid-1990s). Every SSL (Secure Sockets Layer) version is prohibited.
    

    TLS (Transport Layer Security)
    Its IETF (Internet Engineering Task Force) successor. Only TLS (Transport Layer Security) 1.2 and TLS (Transport Layer Security) 1.3 may be used; TLS (Transport Layer Security) 1.0 and 1.1 were deprecated by RFC (Request for Comments) 8996 https://www.rfc-editor.org/rfc/rfc8996.
    

    RFC (Request for Comments) 9846
    The current TLS (Transport Layer Security) 1.3 specification (2026) https://www.rfc-editor.org/rfc/rfc9846, replacing RFC (Request for Comments) 8446 https://www.rfc-editor.org/rfc/rfc8446.
    

    ITSP.40.062 (Information Technology Security Practitioner publication 40.062)
    Canadian guidance https://cyber.gc.ca/en/guidance/guidance-securely-configuring-network-protocols-itsp40062: TLS (Transport Layer Security) 1.3 recommended, TLS (Transport Layer Security) 1.2 where needed, older versions phased out.
    

    "SSL (Secure Sockets Layer) certificate"
    Vendor wording for the same X.509 certificate that TLS (Transport Layer Security) uses.

    2.2 What HTTPS (Hypertext Transfer Protocol Secure) adds to HTTP (Hypertext Transfer Protocol)
    Slide 21What HTTPS (Hypertext Transfer Protocol Secure) adds to HTTP (Hypertext Transfer Protocol)
    

    

    HTTPS (Hypertext Transfer Protocol Secure)
    HTTP (Hypertext Transfer Protocol) carried inside a TLS (Transport Layer Security) connection, normally on TCP (Transmission Control Protocol) port 443.
    

    Confidentiality
    Application data encrypted with a symmetric algorithm (AES-GCM (Advanced Encryption Standard in Galois/Counter Mode) or ChaCha20-Poly1305).
    

    Integrity
    Every TLS (Transport Layer Security) record carries an authentication tag (AEAD (Authenticated Encryption with Associated Data) ciphers only in TLS (Transport Layer Security) 1.3); any change closes the connection.
    

    Server authentication
    The server proves it holds the private key of a certificate the client trusts. mTLS (mutual Transport Layer Security): the client presents a certificate too.
    

    The certificate does not encrypt the traffic
    It authenticates the server's public key; the traffic keys come from a fresh key exchange for every connection.

      4. 

    4. Certificate — the leaf and intermediate certificates.
      5. 

    5. CertificateVerify — the server's signature over the handshake transcript: the proof of possession.
      6. 

    6. Finished — an HMAC (Hash-based Message Authentication Code) over the whole handshake: nothing was modified.
      7. 

    7. The client validates the chain, verifies CertificateVerify and Finished, and sends its own Finished.
      8. 

    8. Application data — encrypted with keys derived by HKDF (HMAC-based Key Derivation Function).

    Slide 23The TLS (Transport Layer Security) 1.3 handshake (2/2)
    

    

    Forward secrecy
    Session keys come from ephemeral key shares deleted after the connection: recorded traffic cannot be decrypted later, even with the stolen server key. Default in TLS (Transport Layer Security) 1.3.
    

    Hybrid key exchange
    X25519 combined with ML-KEM-768 (Module-Lattice-Based Key-Encapsulation Mechanism, parameter set 768) — Chrome's default since version 131 https://security.googleblog.com/2024/09/a-new-path-for-kyber-on-web.html — so recorded traffic also resists a future quantum computer.
    

    


    2.4 Certificates in other secure services
    Slide 24Certificates in other secure services
    

    

    LDAPS (Lightweight Directory Access Protocol over TLS)
    TCP (Transmission Control Protocol) port 636 — directory queries to Active Directory.
    

    SMTP (Simple Mail Transfer Protocol) and IMAP (Internet Message Access Protocol) with STARTTLS
    Mail between servers and mailbox access.
    

    RDP (Remote Desktop Protocol)
    Windows Remote Desktop presents a TLS (Transport Layer Security) certificate.

    OpenVPN and IPsec (Internet Protocol Security) with IKEv2 (Internet Key Exchange version 2) can use certificates; WireGuard (LAB_06) uses none — each peer is a static public key.

    Wi-Fi network and clients authenticate with certificates (Class 13).

    The pfSense or OPNsense web interface over HTTPS (Hypertext Transfer Protocol Secure) (LAB_05).
    

    


    2.5 SSH (Secure Shell): a different trust model
    Slide 25SSH (Secure Shell): a different trust model
    

    

    Host key
    The key pair that identifies an SSH (Secure Shell) server (TCP (Transmission Control Protocol) port 22); it signs the key-exchange data.
    

    Fingerprint check
    On the first connection, compare the key fingerprint with the console value from ssh-keygen -lf.
    

    known_hosts and TOFU (Trust On First Use)
    Accepted keys are stored in ~/.ssh/known_hosts: trust on first use.
    

    Host-key warning
    REMOTE HOST IDENTIFICATION HAS CHANGED! — the server was reinstalled or someone is intercepting; find out which.
    

    User keys
    Public keys listed in ~/.ssh/authorized_keys, better than passwords.
    

    SSH (Secure Shell) certificates
    An SSH (Secure Shell) CA (Certificate Authority) key signs host and user keys: no TOFU (Trust On First Use) needed.
    

    OpenSSH 10.0
    Since April 9, 2025, default key agreement mlkem768x25519-sha256 (hybrid post-quantum) https://www.openssh.org/txt/release-10.0.

      3.1 Why certificates have a life cycle
      Slide 30The certificate life cycle: nine stages
      

      

      Certificate life-cycle management
      Making sure each certificate is issued correctly, replaced before it expires and withdrawn when it must no longer be trusted — because keys get stolen, identities change and algorithms age. A forgotten renewal stops a service.
      

      


      3.2 The nine stages
      

        

      1. Key generation — on the system that will use it, or in an HSM (Hardware Security Module); the private key never goes to the CA (Certificate Authority).
        2. 

      2. Enrollment — a CSR (Certificate Signing Request), signed with the private key: the proof of possession.
        3. 

      3. Validation — the CA (Certificate Authority) or its RA (Registration Authority) checks control of the names; ACME (Automatic Certificate Management Environment) challenges http-01 or dns-01 (RFC (Request for Comments) 8555 https://www.rfc-editor.org/rfc/rfc8555).
        4. 

      4. Issuance — the CA (Certificate Authority) signs; public CAs (Certificate Authorities) log it in Certificate Transparency.
        5. 

      5. Installation — certificate and chain on the server; private key file owner-only.
        6. 

      6. Monitoring — inventory of every certificate and its expiry date; early alerts.
        7. 

      7. Renewal — a new certificate before Not After, with a new key pair: re-keying.
        8. 

      8. Revocation — invalid before its expiry date.
        9. 

      9. Expiry and retirement — no longer valid; the old private key is deleted securely.
        10. 

      


      3.3 How long a certificate may live
      Slide 31How long a certificate may live

      3.4 Revocation
      Slide 32Revocation (1/2): why a certificate is withdrawn
      

      

      Reason codes
      Defined in RFC (Request for Comments) 5280 https://www.rfc-editor.org/rfc/rfc5280: keyCompromise (private key exposed), cACompromise (CA (Certificate Authority) key compromised), affiliationChanged, superseded, cessationOfOperation.
      

      

      Slide 33Revocation (2/2): how clients learn about it
      

      

      CRL (Certificate Revocation List)
      A signed list of revoked serial numbers, published at the CRL (Certificate Revocation List) Distribution Points address; Next Update says when the next list is due.
      

      OCSP (Online Certificate Status Protocol)
      A query about one serial number, answered good, revoked or unknown (RFC (Request for Comments) 6960 https://www.rfc-editor.org/rfc/rfc6960); current, but the CA (Certificate Authority) sees which sites you visit.
      

      OCSP (Online Certificate Status Protocol) stapling
      The server attaches the signed OCSP (Online Certificate Status Protocol) answer to the TLS (Transport Layer Security) handshake.
      

      Browser-distributed revocation data
      Compressed revocation lists downloaded by the browser in the background.
      

      Ballot SC-063 (Server Certificate Working Group ballot 063) (2023)
      OCSP (Online Certificate Status Protocol) optional, CRLs (Certificate Revocation Lists) mandatory for public CAs (Certificate Authorities) https://cabforum.org/2023/07/14/ballot-sc063v4-make-ocsp-optional-require-crls-and-incentivize-automation; Let's Encrypt ended OCSP (Online Certificate Status Protocol) in 2025 https://letsencrypt.org/2024/12/05/ending-ocsp/.

        4.1 There is no single best algorithm, only a best fit
        Slide 38No single best algorithm, only a best fit
        

        

        Assessing a cryptographic system
        Measuring an algorithm, its key size and its implementation against the needs of one application: a VPN (Virtual Private Network) needs a fast cipher and a key exchange, a root CA (Certificate Authority) a long-lived signature key, password storage a slow function, a checksum collision resistance.
        

        


        4.2 The assessment criteria
        Slide 39Criterion 1: security strength
        

        

        1. Security strength
        The work of the best known attack, in bits: n bits ≈ 2n operations (NIST (National Institute of Standards and Technology) SP (Special Publication) 800-57 https://csrc.nist.gov/pubs/sp/800/57/pt1/r5/final).

        Slide 40Criteria 2 and 3: lifetime and guidance
        

        

        2. Protection lifetime
        How long data must stay secret or a signature verifiable — six years for NorthMaple's tax records (CRA (Canada Revenue Agency) https://www.canada.ca/en/revenue-agency/services/tax/businesses/topics/keeping-records/where-keep-your-records-long-request-permission-destroy-them-early.html), so until 2032.
        

        Harvest now, decrypt later
        Recording encrypted traffic today to decrypt it once the key exchange can be broken.
        

        3. Official guidance
        ITSP.40.111 (Information Technology Security Practitioner publication 40.111) v5 https://cyber.gc.ca/en/guidance/cryptographic-algorithms-unclassified-protected-protected-b-information-itsp40111: AES (Advanced Encryption Standard), SHA-2 (Secure Hash Algorithm 2 family), SHA-3 (Secure Hash Algorithm 3 family), ML-KEM (Module-Lattice-Based Key-Encapsulation Mechanism), ML-DSA (Module-Lattice-Based Digital Signature Algorithm) and SLH-DSA (Stateless Hash-Based Digital Signature Algorithm) approved; 112 → 128 bits and RSA-3072 (Rivest-Shamir-Adleman with a 3072-bit modulus) by the end of 2030; classical signatures without a post-quantum replacement phased out by the end of 2035; SHA-1 (Secure Hash Algorithm 1) signatures, MD5 (Message-Digest Algorithm 5), DES (Data Encryption Standard), 3DES (Triple Data Encryption Standard), RC4 (Rivest Cipher 4), SSL (Secure Sockets Layer) 3.0, TLS (Transport Layer Security) 1.0 and 1.1 not acceptable.
        

        

        Slide 41Criteria 4 to 7: speed, use, code, keys
        

        

        4. Performance and size
        Time per operation, key and signature size, handshake bytes, CPU (Central Processing Unit) and battery cost — measured on the target hardware (Example 4).
        

        5. Correct use
        No ECB (Electronic Codebook) mode, never reuse an AES-GCM (Advanced Encryption Standard in Galois/Counter Mode) nonce, never store passwords with one unsalted SHA-256 (Secure Hash Algorithm, 256-bit output) pass.
        

        6. Implementation assurance
        Maintained libraries (OpenSSL https://www.openssl.org/), FIPS (Federal Information Processing Standard) 140-3 modules validated by the CMVP (Cryptographic Module Validation Program) https://csrc.nist.gov/projects/cryptographic-module-validation-program; CIS (Center for Internet Security) Control 3 https://www.cisecurity.org/controls/cis-controls-list requires encryption in transit and at rest.
        

        7. Key management cost
        Generation, storage (TPM (Trusted Platform Module), HSM (Hardware Security Module)), rotation and revocation of the keys.
        

        

        Slide 42Criterion 8: resistance to quantum attacks
        

        

        8. Quantum resistance
        Shor's algorithm would break RSA (Rivest-Shamir-Adleman), DH (Diffie-Hellman) and ECC (Elliptic Curve Cryptography); Grover's algorithm only weakens symmetric keys (AES-256 (Advanced Encryption Standard with a 256-bit key) stays adequate).
        

        Post-quantum standards
        FIPS (Federal Information Processing Standard) 203 (ML-KEM (Module-Lattice-Based Key-Encapsulation Mechanism)) https://csrc.nist.gov/pubs/fips/203/final, FIPS (Federal Information Processing Standard) 204 (ML-DSA (Module-Lattice-Based Digital Signature Algorithm)) https://csrc.nist.gov/pubs/fips/204/final and FIPS (Federal Information Processing Standard) 205 (SLH-DSA (Stateless Hash-Based Digital Signature Algorithm)) https://csrc.nist.gov/pubs/fips/205/final, August 13, 2024; HQC (Hamming Quasi-Cyclic) selected as a backup in March 2025 https://csrc.nist.gov/projects/post-quantum-cryptography.
        

        Canadian roadmap
        Plans by April 2026, high-priority systems migrated by the end of 2031, all systems by the end of 2035 https://cyber.gc.ca/en/guidance/roadmap-migration-post-quantum-cryptography-government-canada-itsm40001.
        

        Hybrid deployments
        Chrome 131 and OpenSSH 10.0 use X25519 + ML-KEM-768 (Module-Lattice-Based Key-Encapsulation Mechanism, parameter set 768); WireGuard offers an optional pre-shared key https://www.wireguard.com/protocol/.

STRENGTH stores the security strength of each system, taken from the NIST (National Institute of Standards and Technology) SP (Special Publication) 800-57 comparable-strengths table of section 4.2.
          2. make_key(). RSA (Rivest-Shamir-Adleman) keys use the standard public exponent 65537 and the modulus size from the name; ECDSA (Elliptic Curve Digital Signature Algorithm) uses curve P-256; otherwise an Ed25519 key is created.
          3. sig_args(). Each family signs differently: RSA (Rivest-Shamir-Adleman) uses PSS (Probabilistic Signature Scheme) padding with SHA-256 (Secure Hash Algorithm, 256-bit output), ECDSA (Elliptic Curve Digital Signature Algorithm) signs a SHA-256 (Secure Hash Algorithm, 256-bit output) hash, Ed25519 needs no parameter. The function returns those parameters so the same loop can time every system.
          4. The measurement loop. For each system, time.perf_counter() times key generation, 200 signatures and 200 verifications; the averages are printed with the signature size and the size of the public key in the DER (Distinguished Encoding Rules) form used inside X.509 certificates.
          5. Reading Part 1. In the recorded run, one signature took 0.389 ms with RSA-2048 (Rivest-Shamir-Adleman with a 2048-bit modulus) and 1.085 ms with RSA-3072 (Rivest-Shamir-Adleman with a 3072-bit modulus), against 0.075 ms with ECDSA (Elliptic Curve Digital Signature Algorithm) P-256 and 0.037 ms with Ed25519; the elliptic-curve signatures are also much smaller: 71 and 64 bytes, against 384 bytes for RSA-3072 (Rivest-Shamir-Adleman with a 3072-bit modulus). RSA (Rivest-Shamir-Adleman) verification is the fastest, 0.036 ms for RSA-2048 (Rivest-Shamir-Adleman with a 2048-bit modulus) - an advantage for clients that verify, not for a busy server that signs every handshake.
          6. APPS. Each tuple names an application, the system it uses, its purpose and the year until which it must stay secure. Change a year and run the script again to see the verdict change.
          7. assess(). Four rules, in order: a fast unsalted hash for passwords must be replaced; below 112 bits until 2030 or below 128 bits after 2030, upgrade; a quantum-vulnerable key exchange protecting data beyond 2031 needs a post-quantum plan (harvest now, decrypt later); a quantum-vulnerable signature relied on after 2035 needs a post-quantum plan.
          8. Reading Part 2. The intranet certificate, the VPN (Virtual Private Network) data cipher, the encrypted folder, the SSH (Secure Shell) host key and the checksums are adequate; the old RSA-2048 (Rivest-Shamir-Adleman with a 2048-bit modulus) certificate must be upgraded because it is used after 2030; the VPN (Virtual Private Network) key exchange and the 10-year root need a post-quantum plan; the password store must be replaced.

          Key terms of Class 15
          TermDefinition
          Public Key InfrastructureThe roles, policies, procedures, software and hardware that create, distribute, validate and revoke digital certificates.
          Digital certificateA signed data structure (X.509 v3) that binds a public key to a subject name for a period and for defined uses.
          Certificate AuthorityThe entity that verifies a requester and signs certificates.
          Root certificateThe self-signed certificate at the top of a hierarchy, trusted because it is in the trust store.
          Intermediate certificateA CA (Certificate Authority) certificate signed by the root, used to sign end-entity certificates.
          Trust storeThe list of root certificates an operating system or browser accepts as trust anchors.
          Root programThe rules and audits a CA (Certificate Authority) must satisfy to be included in a vendor trust store.
          Certificate path validationThe checks a client performs on a chain: signatures, dates, name, constraints, revocation, policy.
          Subject Alternative NameThe extension that lists the DNS (Domain Name System) names and IP (Internet Protocol) addresses a certificate is valid for.
          Self-signed certificateA certificate whose issuer and subject are the same key; nobody else vouches for it.
          FingerprintA SHA-256 (Secure Hash Algorithm, 256-bit output) hash of a whole certificate or key, compared out of band to confirm authenticity.
          Proof of possessionEvidence that the requester or server holds the private key: a signature over fresh data.
          TLS (Transport Layer Security) handshakeThe exchange that negotiates the version and cipher suite, creates session keys and authenticates the server.
          CertificateVerifyThe TLS (Transport Layer Security) 1.3 message in which the server signs the handshake transcript with its private key.
          Forward secrecyThe property that stolen long-term keys cannot decrypt past sessions, because session keys came from ephemeral key shares.
          Cipher suiteThe set of algorithms used by a TLS (Transport Layer Security) connection, for example TLS_AES_256_GCM_SHA384.
          Host keyThe key pair that identifies an SSH (Secure Shell) server.
          known_hostsThe OpenSSH file that stores the host keys a user has accepted.
          Certificate Signing RequestA request that carries a public key and names, signed by the matching private key.
          Renewal and re-keyingObtaining a new certificate before expiry; re-keying also creates a new key pair.
          RevocationDeclaring a certificate invalid before its expiry date.
          Certificate Revocation ListA signed list of revoked serial numbers published by a CA (Certificate Authority).
          OCSP (Online Certificate Status Protocol) staplingThe server attaches a signed, recent OCSP (Online Certificate Status Protocol) answer to the TLS (Transport Layer Security) handshake.
          Security strengthThe work of the best known attack, in bits: n bits means about 2 to the power n operations.
          Harvest now, decrypt laterRecording encrypted traffic today to decrypt it once the key exchange can be broken.
          Post-quantum cryptographyPublic-key algorithms designed to resist attacks by quantum computers: ML-KEM (Module-Lattice-Based Key-Encapsulation Mechanism), ML-DSA (Module-Lattice-Based Digital Signature Algorithm) and SLH-DSA (Stateless Hash-Based Digital Signature Algorithm).
          Hybrid key exchangeA key exchange that combines a classical algorithm, X25519, with a post-quantum one, ML-KEM-768 (Module-Lattice-Based Key-Encapsulation Mechanism, parameter set 768).
